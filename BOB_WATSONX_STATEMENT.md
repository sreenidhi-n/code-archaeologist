# How IBM Bob + WatsonX Were Used
**Code Archaeologist | IBM Dev Day Bob Hackathon 2026**

---

## IBM Bob

Code Archaeologist is built natively for Bob as an **MCP (Model Context Protocol) server**. Bob connects to it over stdio transport — no HTTP, no separate process to manage. The project ships a `.bob/mcp.json` configuration that Bob auto-detects on project open.

```json
{
  "mcpServers": {
    "code-archaeologist": {
      "command": "node",
      "args": ["src/index.js"],
      "alwaysAllow": ["excavate_repo", "git_historian", "dependency_grapher", "docs_generator"]
    }
  }
}
```

**Bob is the runtime, the UI, and the agent.** The developer types a single natural-language instruction in Bob's chat panel:

```
excavate_repo("/Users/sreenidhi/struts1")
```

Bob resolves this to an MCP tool call, passes the arguments through the server's `CallToolRequestSchema` handler, and receives back a structured JSON result it can reason over, summarize, and present. All five phases run inside the MCP server process — Bob never touches the filesystem or git directly.

Bob also observes **real-time phase progress** via the server's stderr stream (`[Code Archaeologist] Phase 2/5: Historical Excavation — COMPLETE (2.1s)`), giving the developer live feedback as the excavation runs.

## IBM WatsonX — Granite Model Usage

Every AI narrative in Code Archaeologist is generated by **WatsonX Granite** via the WatsonX ML REST API (`/ml/v1/text/generation`). The integration uses IAM token authentication with automatic caching and retry on 429/503 responses.

**Model:** `ibm/granite-4-h-small` (configured via `WATSONX_MODEL` env var; falls back to `ibm/granite-3-8b-instruct`)

**All prompts use the Granite instruct chat format** to prevent instruction echoing:
```
<|system|>
{system role}
<|user|>
{task}
<|assistant|>

```

### The 6 WatsonX Calls Per Excavation (all structured, all with template fallbacks)

| Call | What Granite Does | Tokens |
|------|-------------------|--------|
| **Phase 2 — Git narrative** | Given contributor stats, writes a 3–4 sentence "human story" of who built the codebase and what risks their departure created | ~200 |
| **Phase 2 — Knowledge Obituary** (×N departed contributors) | Given a contributor's commit history and orphaned files, writes a 2–3 sentence institutional-knowledge obituary | ~120 each |
| **Phase 3 — Structural observation** | Given LOC/test-ratio/directory-depth metrics, writes 2–3 sentences on architectural risks | ~120 |
| **Phase 4 — Risk narrative** | Given CVE list and risk score, writes a 3–4 sentence security assessment naming specific vulnerable packages | ~200 |
| **Phase 5 — Executive summary** | Synthesizes git history + CVE data into a 3–5 sentence briefing for a developer about to inherit the codebase | ~250 |
| **Phase 5 — High-risk file analysis** (×3 files) | Granite reads actual source code (first 150 lines of highest-churn files) and writes: what it does, implicit knowledge required, highest-risk aspect | ~150 each |
| **Phase 5 — C5 cross-ref advisories** (top 3 intersections) | Given files that are BOTH CVE-affected AND orphaned by departed developers, writes 2-sentence urgent advisory per file | ~350 |
| **Phase 5 — Where to start** | Writes a 4–5 step onboarding checklist referencing actual file names, CVE IDs, and contributor names from the data | ~300 |

### Why Granite Specifically

Granite is **the only model used** in this project — no llama, no mistral, no other family. The structured instruct format means Granite responses stay focused and don't echo back prompt fragments. The `ibm/granite-4-h-small` variant balances speed (critical for the <10s total excavation budget) with output quality for technical prose.

### Template Fallbacks

Every WatsonX call has a fully deterministic template fallback. If the API is unavailable — bad credentials, network timeout, rate limit — Code Archaeologist still produces a complete, useful report. The fallback is indicated in the `narrativeSource` field (`'watsonx'` vs `'template'`) on every output, so users always know the provenance of each section.

## Integration Architecture

```
Bob IDE chat
    │  "excavate_repo('/path/to/struts1')"
    ▼
MCP CallToolRequest (stdio)
    │
    ▼
src/index.js — validates args, routes to tool
    │
    ├── gitHistorian.js ──────────────────────► WatsonX (narrative + obituaries)
    │   └── git log (spawn, streaming)
    │
    ├── dependencyGrapher.js ─────────────────► WatsonX (risk narrative)
    │   ├── pom.xml parse (fast-xml-parser)
    │   └── OSV.dev CVE feed (parallel fetch)
    │
    └── docsGenerator.js ─────────────────────► WatsonX (summary + file analysis
        ├── analyzeHighRiskFiles()                        + C5 advisories + roadmap)
        └── crossRefCvesAndOrphans() [C5]
                │
                ▼
         ONBOARDING.md + EXCAVATION_REPORT.md
         written to analyzed repo root
```

Bob receives the complete structured result, can ask follow-up questions about specific CVEs or contributors, and presents the key findings directly in the IDE chat panel — no context switching required.
