# How IBM Bob + WatsonX Were Used
**Code Archaeologist | IBM Dev Day Bob Hackathon 2026**

---

## IBM Bob

Code Archaeologist is built natively for Bob as an **MCP (Model Context Protocol) server** over stdio transport. The project ships a `.bob/mcp.json` config that Bob auto-detects on project open — no HTTP server, no separate process.

The developer types one instruction in Bob's chat panel:

```
excavate_repo("/Users/sreenidhi/struts1")
```

Bob resolves this to an MCP tool call, passes arguments through the server's `CallToolRequestSchema` handler, and receives a structured JSON result it reasons over and presents. All five excavation phases run inside the MCP server process — Bob never touches the filesystem or git directly. Live phase progress arrives via stderr (`Phase 2/5: Historical Excavation — COMPLETE (2.1s)`), giving real-time feedback as the excavation runs. Bob can then ask follow-up questions about specific CVEs or contributors with full context already loaded.

## WatsonX Granite

Every AI narrative is generated by **WatsonX Granite** (`ibm/granite-4-h-small`, falling back to `ibm/granite-3-8b-instruct`) via the WatsonX ML REST API with IAM token authentication and automatic retry on 429/503 responses.

Granite is the **only model used** — no llama, no mistral. All prompts use the Granite instruct chat format (`<|system|>` / `<|user|>` / `<|assistant|>`) to prevent instruction echoing. Per excavation, Granite makes up to 8 calls: a git history narrative, per-contributor Knowledge Obituaries, a structural risk observation, a CVE risk assessment, an executive summary, source code analysis of the 3 highest-churn files, C5 cross-reference advisories, and a prioritized onboarding checklist.

Every call has a fully deterministic template fallback — if the API is unavailable, Code Archaeologist still produces a complete report. The `narrativeSource` field on every output shows `'watsonx'` vs `'template'` so provenance is always transparent.
